# The key

A key names what a dependency's compiled output *depends on*, so that two
machines computing the same key can share one object. It is the store's
compatibility contract: every producer and every consumer of a store must
compute it identically, or one of them serves bytes the other should not have
accepted.

The key is a hash of **inputs**, never of output. Hashing the output — module
names, beam counts, export sets — fails twice over. It is unsound (measured:
`oban` has an identical module set across six consumers while
`Mix.Tasks.Oban.Install` gains five functions in one of them), and more
fundamentally an output hash can only be computed *after* compiling, which is the
cost being avoided. Output hashes address objects; input hashes are keys.

Every input is either the lock entry or a field of the `%Mix.Dep{}` Mix itself
converged. Nothing is re-derived, because every rule depdep used to re-derive was
a rule Mix owns and depdep got slightly wrong.

## The schema version {#schema}

Every key begins with a schema version, and the current one is `v3`.
`Depdep.Key.schema/0` returns it.

The version is a key input, not merely a path prefix. A change to what an object
*contains*, or to what its key *means*, therefore retires every object in every
store rather than mixing shapes. Objects of two schemas never collide and never
match.

**Changing it invalidates every consumer's store at once.** It is a breaking
change in the semver sense: it requires a major version and a migration note.

| Version | What changed | Consequence |
|---|---|---|
| `v2` | objects gained `deps/` alongside `_build/` | an object's contents changed |
| `v3` | the key's inputs became Mix's own: `env:`, `compile:` and `system_env:` joined it, and the toolchain gained ERTS, architecture and the compiler environment | no `v2` object can be trusted to have been built the way a `v3` key says |

A consumer adopting a depdep that raises the schema sees one cold run per store
while the new paths fill. That is the intended cost of the guarantee, not a
regression.

```test schema-in-key
given two keys computed identically but for the schema version
then they differ
and no object of one schema is reachable by a key of the other
```

## Why the key recurses {#recursion}

A dependency's compiled output is a function of its dependencies' compiled
output, not only of its own source. Elixir resolves a great deal at compile time
and bakes the result into the caller's bytecode:

- **Macros.** `use Spark.Dsl` expands spark's macro bodies *into* ash's modules;
  ash's beams literally contain code generated by spark.
- **Struct literals.** `%Spark.Dsl.Entity{}` in ash's source inlines spark's
  field list as a literal map in ash's beam.
- **Compile-time evaluation.** `@x Foo.bar()` at module level freezes a value.

So bumping `spark` changes what ash's *correct* bytecode should be while ash's own
version and checksum stay byte-identical. A flat `<dep>:<version>` key serves the
stale ash forever and nothing detects it, because dependency staleness is decided
from the lock entry and the SCM and nothing about the surrounding dependency set.

Mix gets this right in a normal build: it tracks compile-time dependencies and
recompiles dependents. **A cache restore steps around that machinery entirely.**
The key therefore has to re-establish, at the cache layer, the invariant Mix
maintains at the compile layer. That is the whole argument for the recursion.

The recursion is also what buys **precision**. The other sound key — hash the
whole lockfile — invalidates every package on any lock change whatsoever. Under
the recursion, bumping `spark` invalidates spark and the packages above it and
leaves `postgrex`, `telemetry` and `bcrypt_elixir` alone.

```test recursion-precision
given a lock where one dependency is bumped
when every key is recomputed
then the bumped dependency and its dependents change
and a dependency that does not reach it is unchanged
```

## What the key hashes {#inputs}

`Depdep.Key.compute/3` returns `%{name => {:key, hash} | {:skip, reason}}` for
every entry in the lock. `Depdep.Key.digest/1` is the hash: SHA-256 over the
parts joined by newlines, hex-encoded lower case.

The parts, in order:

```
schema_version
elixir, otp, erts, arch, mix_env,
ERL_COMPILER_OPTIONS, ELIXIR_ERL_OPTIONS, MIX_TARGET
[os_release, cc]                     # only for a dependency with a native build
name, version, inner_checksum
build_tools
env, compile, system_env
config_digest(app)
for each declared child, sorted:
  optional and absent -> ("absent", name)
  otherwise           -> ("present", name, key(child))
```

The dependency's own source comes from its lock entry:
`Depdep.Lock.version/1`, `Depdep.Lock.inner_checksum/1` and
`Depdep.Lock.build_tools/1`, read from the map `Depdep.Lock.read/1` returns.

For a hex entry the inner checksum is hex's own. For a git entry it is the ref
sha, which is a **stronger** identity than hex's checksum: it names the exact
tree rather than a tarball somebody assembled from it. A git entry records no
build tools, so `Depdep.Lock.build_tools/1` answers the constant `git` — absent
would change the key's shape between the two kinds, and a constant does not.

## The toolchain fingerprint {#toolchain}

`Depdep.Key.toolchain/1` returns `%{base: parts, native: parts}`.

`base` is in every key: the Elixir and OTP the bytecode was produced by, the ERTS
version and the architecture a beam or NIF is loaded into, the `MIX_ENV`, and the
three environment variables that change what the compilers emit —
`ERL_COMPILER_OPTIONS`, `ELIXIR_ERL_OPTIONS` and `MIX_TARGET`. An unset variable
reads as empty, so unset is one value rather than a missing part.

Before `v3` only Elixir, OTP and the env were here. Every NIF object in every
store was x86-64 bytes with nothing in its key saying so.

## Native builds {#native}

`native` is folded into a key only for a dependency whose build produces native
code, and `Depdep.Key.native?/1` decides which those are. It adds the OS release
and the C compiler version, because those are what such a dependency's bytes
additionally depend on.

A dependency **without** a native build does not rekey when the image's `gcc`
moves. That is why the two halves are separate rather than one list.

`Depdep.Key.native?/1` answers from the lock entry alone, fetched or not: a
native build is driven by a tool the dependency declares — `elixir_make`,
`rustler`, `rustler_precompiled`, `zigler`, `zigler_precompiled` or
`cc_precompiler` — or the dependency is `make`-managed, which
`Depdep.Lock.hex?/1` and the entry's build tools establish. Those names are in
the lock entry's child list, so this needs no source on disk.

`rustler_precompiled` downloads a build for the target rather than compiling
one. It counts as native anyway: the bytes are still native bytes, still
target-specific.

A machine with no C compiler reports `none` rather than omitting the part, so a
machine that gains a compiler later cannot match objects built without one.

```test native-only-native
given one dependency with a native build tool and one without
when the C compiler version changes
then the native dependency's key changes
and the other dependency's key does not
```

## Build options the declaration carries {#build-options}

`env:`, `compile:` and `system_env:` are key inputs. A dependency compiled under
an `env:` other than `:prod`, with a custom `compile:` command, or with
`system_env:` set produces different bytecode from identical source.

They are read from the `%Mix.Dep{}` Mix converged, not from any file depdep
parses. `Depdep.Deps.mix_dep_fields/0` names every field of Mix's struct this
depends on, so a change in Mix's internals fails a test rather than silently
changing keys.

A transitive dependency Mix has not yet listed takes the defaults, and that is
correct rather than approximate: only a **top-level** declaration can set these
options, and top-level dependencies are in Mix's list whether fetched or not.

```test hex-key-stable-across-passes
given a transitive hex dependency
when its key is computed before mix deps.get and again after
then the two keys are equal
```

## Compile-time configuration {#config}

Each node contributes the digest of the compile-time configuration reaching its
own app, via `Depdep.Config.digest_for/2`. Because each node folds in its
children, a dependency's closure accumulates configuration for exactly the apps
in that closure and no others: configuring an app outside the closure leaves the
key alone.

An unconfigured app and an app configured to `[]` digest identically — there is
no distinction to preserve between them.

## Children, present and absent {#children}

A child is recorded by name and by its own key. A child **absent from the lock**
is an unresolved optional dependency, and its absence is recorded **positively**
as `absent <name>` rather than omitted.

Absence is what changes the parent's compiled output: `ash` guards whole source
files on `Code.ensure_loaded?(Plug)`. A key that omitted an absent optional
would collapse the with-Plug and without-Plug builds onto one object.

Children are sorted, so the key does not depend on declaration order.

```test absent-optional-positive
given a package with an optional dependency
when the optional dependency is absent from the lock, and again when present
then the two keys differ
```

## What cannot be keyed {#skip}

A dependency resolves to `{:key, hash}` or `{:skip, reason}`.

A git dependency that Mix has not fetched is skipped: its children are unknown
until `mix deps.get`, and a key computed without them would be a claim depdep
cannot support. Once Mix lists its children it is keyed like anything else.

**`:skip` propagates upward.** A dependency whose child cannot be keyed cannot
itself be keyed, because its own output depends on that child's. This is the
fail-safe direction: it costs a compile, never a wrong restore.

A cycle returns `{:error, {:cycle, name}}` rather than looping. Hex's resolver
cannot produce one, so this guards a malformed lock rather than an expected
state — but the alternative is a hang with no explanation.

```test skip-propagates
given a dependency that cannot be keyed
then every dependency that reaches it is also skipped
and each skip names what it could not key
```

## What an object carries and the key does not hash {#not-hashed}

Two things travel inside an object deliberately unhashed.

Mix's Erlang compiler manifest records the **pusher's absolute beam paths**. It
is read only when Mix decides to recompile the dependency, and then it makes Mix
recompile the `.erl` files it lists — a few files, once, never a wrong build.
Mix's Elixir manifest records relative source paths and the directory it was
compiled in, and Mix checks it only when compiling.

Neither changes what a restored dependency *is*, so neither belongs in the key.
What notices that Mix would rebuild a restored unit — for these reasons or any
other — is the restore check, specified in `spec/06-the-run.md`.

## Where an object lives {#object-path}

`Depdep.Key.object/3` gives an object's path:
`<schema>/<name>/<version>/<hash>.tar.gz`.

Readable rather than flat, so a store can be browsed and a human can see what is
in it. The schema leads, which is what makes retiring a schema a matter of
writing under a new prefix rather than deleting anything.
